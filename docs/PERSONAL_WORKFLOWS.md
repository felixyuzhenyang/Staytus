# Personal facts, application stages and guided chat

## Implemented in this iteration

The existing owned profile now has an optional, typed `planning_details` JSON object in Supabase PostgreSQL. Alembic revision `20261103_0002` adds it with an empty-object default, preserving existing accounts and records. Unknown facts remain unknown; no live user's immigration details are filled in by the operator. The same conditional form is used in onboarding and Profile settings.

- F-1 activity (studying, post-completion OPT, STEM OPT, other/unknown) is separate from the application being tracked. A current OPT user can be preparing a STEM extension without overwriting their current EAD facts.
- OPT stages: unknown, not planning, considering, preparing, submitted, approved, active, completed, denied or withdrawn. The tracked type is pre-completion, initial post-completion or STEM extension. Optional facts include school-confirmed academic completion, DSO recommendation, application submission, requested start and current EAD start/end. Adviser-review answers are user-reported facts, not a grant of eligibility.
- Shared planning facts: next plan, extension stage/requested end, travel destination/return, passport/entry-visa expiry, whether a visa application is planned, I-94 D/S versus a dated admission and its date. No passport, visa, I-94, SEVIS or USCIS receipt identifying numbers are collected.
- J-1 student Academic Training stages and proposed/authorized dates remain separate from OPT. J-1 scholar category, sponsor and host department are recorded separately; scholar profiles cannot save student training fields.

Inputs are validated on create and after merging a partial update with saved data. Invalid EAD/training ranges, return before departure, unsupported fields and incompatible categories are rejected before persistence. Explicit null clears a fact. Category changes clear incompatible planning facts; the form explains this. Profile version increments invalidate prior action approvals, and the next authenticated chat/tool call receives the current structured profile.

### Progressive Profile form (November 8)

Onboarding and My Profile mark required basics with `*`; update frequency has a default, and all planning details are optional. Considering OPT shows the stage and type without requesting recommendation, submitted-application or requested-OPT dates. Preparing and later stages expose those known dates in a collapsed application section, with separate labels for a planned request and an already requested start. This date is distinct from an intended internship start and from approved EAD dates.

EAD dates are in a separate collapsed section for users who already have an OPT authorization card, including those considering a STEM extension on an existing card. Concise DSO/EAD definitions link to Penn/USCIS. Academic dates, extension/next plans, travel/document dates and admission/adviser checks also start collapsed. Collapsing does not clear values. Controlled planning fields preserve unsaved edits across OPT-stage changes; saved application dates hidden in Considering remain retained, with an explanatory note. Users can review/clear those dates by selecting the relevant application stage. The form does not migrate or silently rewrite historical dates or change filing-window rules.

`business_planning.py` provides deterministic stage selection and record checks, shared by the existing workflow guidance/dashboard/agent action-plan path. Submitted applications get receipt/progress and adviser-follow-up steps instead of an initial application checklist. Approved/active applications prompt EAD/date/reporting review. Not-planning/completed extension stages suppress the old extension-preparation target. Missing facts remain visible questions. Travel checks compare saved expiry dates with **return**, flag travel while an OPT application is pending and keep visa expiration distinct from authorized stay.

Additional internal planning targets feed the existing reminder inbox and opted-in digest pipeline: considering/preparing OPT produces a 60-day preparation buffer when the relevant date is known (academic completion for initial post-completion OPT, requested start for pre-completion OPT, current EAD end for STEM extension). Current/approved OPT with a saved EAD end produces a 30-day EAD-review buffer; authorized/active Academic Training with a saved end produces a 30-day sponsor-review buffer. These are configurable school-adapter product preferences, not legal windows. Submitting an application removes its preparation target; removed targets supersede existing unsent planning notices on the next reminder synchronization. Existing account-scoped scheduling, consent and Brevo delivery remain unchanged. This iteration does not claim a real personal reminder email or a real provider calendar write was performed.

## Legal-rule boundary and sources checked

No new legal deadline, grace-period countdown, eligibility approval or travel clearance is activated. Sources retain the existing capture/review/freshness gates; a fetched page or an LLM response cannot change active rules. The rule trace includes `business-planning-2026-11-03-v1`. Legal calculations need an explicitly reviewed, version-bound rule and all applicable facts; a general school page or an old numerical constant is not sufficient.

Primary pages inspected on 2026-11-03: [Penn OPT guide](https://global.upenn.edu/isss/opt/), [Penn STEM OPT](https://global.upenn.edu/isss/opt-stem/), [Penn travel](https://global.upenn.edu/isss/home/immigration/travel/) and [Penn final-rule resource center](https://global.upenn.edu/isss/dhs-final-rule-resource-center/). The USCIS OPT/STEM pages returned HTTP403 through the research tool. Conflicting/evolving guidance must be reviewed rather than silently converted into a filing rule. Signature validity depends on activity, document and re-entry circumstances; saving a signature date does not automatically establish permission to travel. This iteration intentionally does not turn a signature anniversary into an automatic legal conclusion.

## Guided requests in chat (implemented)

### Visual planning timelines (November 8)

Guided forms and ordinary chat planning now share a server-owned timeline. The interactive Orchestrate Agent returns a typed answer/planning envelope for free-text requests. Explicit new scenario facts require a verbatim quote from the current user message; dates are independently checked against that quote, category-incompatible facts are rejected, and intended internship goals remain separate from requested OPT dates. A definition or policy-source lookup can return an ordinary answer without a timeline. Same-topic follow-ups may reuse a current-version scenario; a different topic does not automatically inherit it.

The backend builds a fixed safety sequence with dates, calculation traces, dependency links and official-source capture/review metadata. It also derives a private allowlist of scenario-specific candidate steps from deterministic record conflicts and missing-information checks. Orchestrate then generates a brief summary, explains every core node and may select zero to three candidate IDs that materially improve this user's plan. Candidate title, timing, placement, dependencies, sources and calendar eligibility stay server-owned; the model supplies only the selection and explanation. Selected steps receive an **Added for your situation** label after allowlist and text validation. Invalid optional selections are discarded after one repair when the core plan is still valid.

JSON shape, core-node identity/completeness, candidate IDs and supported timing/action claims are validated. Equivalent ID-keyed notes are losslessly normalized without inventing text or missing nodes. Unsupported core output produces an error rather than a fabricated plan. Source review and legal correctness still require separate confirmation; this is not a legal filing-window engine. Undated or unverified filing steps remain **To confirm**. Calendar actions use only the existing deterministic preparation targets and existing approval path.

The OPT form includes an optional **Intended internship / employment start** stored only with that conversation's scenario. For Penn considering/preparing/unknown OPT stage, this goal can supply a labelled internal 60-day preparation target when no other OPT preparation target exists. It does not populate `opt_requested_start`, update Profile or alter ongoing scheduled reminders. A past preparation target is explicitly moved to review-today with the original calculation retained.

The chat displays the LLM summary followed by a vertical sequence of expandable milestones. Each shows its date category (preparation target, saved date, personal goal, process step or To confirm), short AI explanation, date basis, dependencies and official reference links with capture status. Contextual nodes also show why the backend made that option available. Sequence spacing does not represent elapsed time. Plan metadata and explanations persist in the existing conversation JSON, restoring the same timeline after refresh; older text-only plans still render. A profile version change disables the old calendar actions. No database migration, new provider credential or cloud-tool import is needed.

Try **My Assistant → Plan OPT / EAD**, enter the intended start and known application details, and generate a plan. Or type: `I am considering pre-completion OPT and want to start an internship on May 20, 2027. Please plan my timeline.` Open **Date basis and official sources** on a node. Missing filing information should show To confirm. A normal definition such as `What does DSO stand for?` should not force a timeline. The opt-in probe `scripts/verify_planning_timeline.py --confirm-synthetic-test` exercises the actual model using fictional users and exact-row cleanup; `--local` runs the current backend against the existing runtime before deployment.

The Assistant now has persistent workflow shortcuts and intent-specific forms: international travel, F-1 OPT/EAD, extension, J-1 student Academic Training and J-1 scholar appointment review. The last two and OPT are shown only for their corresponding saved status. For example **Plan a trip abroad**:

1. Prefill saved departure, return, destination, document dates, activity and application stage. The form explicitly says overrides are used for this plan only; Profile remains the place to save ongoing reminder facts. Unknown travel dates/destination can remain blank and appear as To confirm in the timeline; inconsistent supplied dates are rejected.
2. Send typed `planning_request` data with the saved profile version to the existing authenticated `POST /chat`. The server rejects stale versions, incompatible categories and inconsistent merged dates before calling the model. A temporary scenario combines the current owned profile and supplied fields without changing persistent profile facts.
3. Retrieve scoped real policy excerpts and supply the scenario, workflow record checks, missing questions and internal calendar targets to the same real Orchestrate runtime. The LLM writes the personalized explanation using the request's language; source capture/review labels and calculation traces are rendered directly from backend metadata. The model must acknowledge missing facts and avoid inferring legal windows, travel permission or eligibility. Calendar buttons use deterministic backend targets rather than dates extracted from free-form model prose.
4. Each plan offers preparation-reminder buttons using the existing calendar destination picker and exact-content approval. The user can choose an export or an already authorized provider, inspect the date/account/content and approve once. No calendar write occurs when a plan is generated. Expired internal preparation dates become a labelled review-today target, not a newly asserted deadline.

Live testing showed that this tenant could prioritize tool-derived saved facts over supplemental history. Guided requests therefore repeat a bounded scenario/evidence package in the current model turn. A narrow generated-text check flags unsupported dates/durations, certain execution claims and a known source-review misstatement, including Unicode date punctuation. One model correction is allowed; if it still fails, the route returns an error and saves no successful plan. This is not comprehensive legal/factual validation. The complete source review and eligibility boundaries still apply.

Successful user/assistant turns, structured plan metadata and source references persist in the existing account-owned conversation JSON; no schema migration or extra model credential is needed. `GET /chat/history` restores the latest successful conversation on a return visit. Follow-up questions keep the temporary scenario while its base profile version is current. Profile changes invalidate that scenario and disable old calendar buttons. Temporary plan details do not automatically change the scheduled email-reminder pipeline: save them in Profile for recurring monitoring. Conversation history currently retains up to40turns; this is not a separate permanent plan archive.

Do not label ordinary travel as an I-20 visa application: the workflow distinguishes a school document/travel endorsement from an entry-visa application. Source status and blocked/unavailable captures remain visible; retrieval does not prove comprehensive coverage. Proactive LLM messages are implemented separately below.

## Proactive assistant messages (implemented)

A web page does not need to be open for the server to create a message. A separate daily cloud job and durable generation outbox now use the existing planning/policy reminders as event producers:

- A source-change or personal-planning event is matched to an owned profile. A content change is first labelled a detected change, not an effective legal policy or a confirmed personal impact.
- A unique key binds account, event, profile version and policy version. A bounded, retryable generation job gets only permitted profile facts and official evidence; mailbox previews remain excluded without their separate consent.
- The model writes a structured summary (what changed, why it may matter, unknown facts, next action, source links). Store it as a clearly labelled proactive assistant message with provenance. Do not insert a fabricated user question or trust generated HTML.
- The account-owned assistant-updates API returns persisted messages inside the chat area on the next visit, with unread status and a discussion action. Existing email digests remain separate; this iteration does not change email content or send a new email.
- On profile/source changes, invalidate stale generation work. Apply idempotency, token budgets and batching so each website edit does not trigger every user's LLM call. Never execute a calendar/email/application action because a background summary requested it.

No new multi-agent deployment is required. The server owns events, authorization and persistence. Background explanations use the configured watsonx.ai model; interactive chat and user-requested follow-up continue through Orchestrate. See [proactive assistant operations](PROACTIVE_ASSISTANT.md) for the delivered limits and verification.
